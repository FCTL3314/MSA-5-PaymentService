# Задание 1. Шаги Saga-оркестрации платежа

Процесс: пользователь оформляет заказ и инициирует платёж. Деньги списываются с его счёта, затем идёт антифрод-проверка. Если проверка пройдена, деньги переводятся контрагенту. Если операция подозрительная, она блокируется, клиенту сразу возвращаются деньги, а служба безопасности получает уведомление.

Оркестратор — Camunda (BPMN, см. [Task3](../Task3/ADR.md) и [Task4.1](../Task4.1)). Он вызывает шаги по очереди, хранит состояние Saga и при сбое запускает компенсации в обратном порядке.

## Реестр транзакций Saga

| Транзакция | Описание | Тип | Компенсация |
|---|---|---|---|
| `CREATE_PAYMENT` | **Payment Service.** Создаёт платёж в статусе `CREATED`: сумма, валюта, клиент, контрагент, ключ идемпотентности по `orderId`. Повторный запрос с тем же заказом возвращает уже созданный платёж. С этого шага стартует экземпляр Saga | компенсируемая | `CANCEL_PAYMENT` |
| `RESERVE_LIMITS` | **Сервис контроля ограничений.** Проверяет лимиты клиента (на операцию, суточный, месячный) и резервирует сумму. При превышении возвращает бизнес-ошибку `LIMIT_EXCEEDED`, и Saga уходит в компенсацию ещё до списания денег | компенсируемая | `RELEASE_LIMITS` |
| `DEBIT_FUNDS` | **Payment Service → банк / платёжный шлюз.** Списывает деньги со счёта клиента на транзитный счёт платформы. Ключ идемпотентности — `debit:{paymentId}`. При таймауте сначала запрашивается статус операции в банке, повторное списание не делается. Отказ банка (`DEBIT_DECLINED`: нет средств, карта заблокирована) запускает компенсацию | компенсируемая | `REFUND_FUNDS` |
| `FRAUD_CHECK` | **FraudCheck Service.** Проверяет транзакцию по внутренним правилам и у внешних провайдеров (AML, GeoRisk) с таймаутами, retry и кэшированием результата в Redis. Возвращает `ALLOW`, `DENY` или `MANUAL_REVIEW`. Если ответа нет до cut-off-time, транзакция по умолчанию считается разрешённой. Шаг только читает данные, поэтому откатывать в нём нечего | компенсируемая | — (компенсация не нужна: шаг без побочных эффектов) |
| `MANUAL_FRAUD_REVIEW` | **FraudCheck Service, оператор антифрода.** Если пришёл ответ `MANUAL_REVIEW`, платёж ждёт решения оператора `ALLOW` / `DENY`, на решение есть 20 минут. Когда истекает cut-off (20 минут), транзакция считается разрешённой. Пока платёж ждёт, клиент может его отменить | компенсируемая | — (компенсация не нужна: шаг без побочных эффектов) |
| `TRANSFER_TO_MERCHANT` | **Payment Service.** Переводит деньги с транзитного счёта на счёт контрагента. **Pivot-транзакция.** После неё Saga обязана дойти до конца. Технические ошибки повторяются с тем же ключом `transfer:{paymentId}`. Если банк отказал в переводе (`TRANSFER_REJECTED`, например счёт контрагента закрыт), деньги контрагенту не ушли, и Saga компенсирует предыдущие шаги | необратимая | — (после перевода откатить нельзя; возврат денег уже ушедших контрагенту — отдельный процесс пост-фактум возврата) |
| `COMPLETE_PAYMENT` | **Payment Service.** Переводит платёж в `COMPLETED` и публикует событие для отдела «Финансы» (сверка, отчётность) | повторяемая | — |
| `NOTIFY_CUSTOMER` | **Notification Service.** Уведомляет клиента о результате: успех, блокировка с возвратом, отказ или отмена. Отправка идемпотентна по `notify:{paymentId}:{template}` | повторяемая | — |
| `REFUND_FUNDS` | **Payment Service → банк.** Компенсация `DEBIT_FUNDS`: возвращает деньги с транзитного счёта клиенту. Идемпотентно по `refund:{paymentId}` и повторяется до успеха с экспоненциальной задержкой. Поддержка в ручном режиме не нужна | повторяемая | — |
| `RELEASE_LIMITS` | **Сервис контроля ограничений.** Компенсация `RESERVE_LIMITS`: снимает резерв лимита | повторяемая | — |
| `CANCEL_PAYMENT` | **Payment Service.** Компенсация `CREATE_PAYMENT`: переводит платёж в финальный статус с причиной. `REJECTED` — деньги не списывались. `BLOCKED` — мошенничество, деньги возвращены. `CANCELLED` — отмена клиентом или отказ в переводе, деньги возвращены | повторяемая | — |
| `NOTIFY_SECURITY` | **Notification Service → служба безопасности.** При запрете антифрода, автоматическом или от оператора, отправляет данные операции на анализ. Выполняется параллельно с возвратом денег | повторяемая | — |

Компенсирующие транзакции (`REFUND_FUNDS`, `RELEASE_LIMITS`, `CANCEL_PAYMENT`) сами по себе повторяемые. Они идемпотентны и не могут завершиться бизнес-ошибкой. Технический сбой повторяется до успеха, а если ретраи исчерпаны, создаётся инцидент в Camunda с алертом SRE. Поддержке ничего не нужно делать вручную.

## Сценарии и компенсации

Компенсации выполняются в обратном порядке. Срабатывают только компенсации шагов, которые успели завершиться. Camunda делает это сама через compensation boundary events (см. [BPMN](../Task4.1)).

| Сценарий | Где остановились | Компенсации (в порядке выполнения) | Итоговый статус |
|---|---|---|---|
| Успех | — | — | `COMPLETED` |
| Превышен лимит | `RESERVE_LIMITS` → `LIMIT_EXCEEDED` | `CANCEL_PAYMENT` | `REJECTED` |
| Банк отказал в списании | `DEBIT_FUNDS` → `DEBIT_DECLINED` | `RELEASE_LIMITS` → `CANCEL_PAYMENT` | `REJECTED` |
| Антифрод запретил | `FRAUD_CHECK` → `DENY` | `REFUND_FUNDS` → `RELEASE_LIMITS` → `CANCEL_PAYMENT`, параллельно `NOTIFY_SECURITY` | `BLOCKED` |
| Ручная проверка: оператор разрешил | `MANUAL_FRAUD_REVIEW` → `ALLOW` | — | `COMPLETED` |
| Ручная проверка: оператор запретил | `MANUAL_FRAUD_REVIEW` → `DENY` | `REFUND_FUNDS` → `RELEASE_LIMITS` → `CANCEL_PAYMENT`, параллельно `NOTIFY_SECURITY` | `BLOCKED` |
| Ручная проверка: прошло 20 минут | cut-off → разрешено по умолчанию | — | `COMPLETED` |
| Антифрод не ответил | cut-off → разрешено по умолчанию | — | `COMPLETED` |
| Клиент отменил платёж во время ручной проверки | `MANUAL_FRAUD_REVIEW` прерван | `REFUND_FUNDS` → `RELEASE_LIMITS` → `CANCEL_PAYMENT` | `CANCELLED` |
| Контрагенту невозможно перевести | `TRANSFER_TO_MERCHANT` → `TRANSFER_REJECTED` | `REFUND_FUNDS` → `RELEASE_LIMITS` → `CANCEL_PAYMENT` | `CANCELLED` |
| Технический сбой после pivot (уведомление, смена статуса) | `COMPLETE_PAYMENT` / `NOTIFY_CUSTOMER` | компенсаций нет, шаг повторяется до успеха | `COMPLETED` |

## Почему так

- **Pivot — перевод контрагенту.** До него все шаги можно откатить: деньги лежат на транзитном счёте платформы. После перевода деньги у контрагента, и вернуть их можно только отдельным процессом возврата. Поэтому все проверки стоят до pivot, а после него остаются только повторяемые шаги. Так требование «стоимость ошибки при проведении выше, чем потеря от отклонения» выполняется самим порядком шагов: пока есть сомнения, деньги контрагенту не уходят.
- **Деньги не зависают между системами.**
  - Все денежные операции (`DEBIT_FUNDS`, `TRANSFER_TO_MERCHANT`, `REFUND_FUNDS`) идемпотентны по ключу операции, и при таймауте сначала запрашивается её статус.
  - Состояние Saga хранит Camunda, поэтому после рестарта процесс продолжается с того же шага.
  - Деньги между списанием и переводом лежат на транзитном счёте, остаток которого по каждому завершённому платежу должен быть нулевым. Это проверяет fitness-функция из [Task6](../Task6).
- **Cut-off-time.** Это явное бизнес-правило: если проверки не ответили вовремя, транзакция разрешается и проводится. Риск закрывается так:
  - поздний ответ антифрода не теряется и записывается;
  - если поздний ответ — `DENY`, запускается отдельный процесс пост-фактум возврата, он уже есть в MVP;
  - значения cut-off вынесены в настройки процесса.
- **Ручная проверка — ожидание внутри Saga.** Состояние «ждём оператора» хранится в Camunda как user task с таймером на 20 минут. Оператор работает в Tasklist, а не в отдельной системе.
- **Внешние вызовы.** Каждый шаг вызывается с таймаутом. Технические ошибки ретраятся с экспоненциальной задержкой, бизнес-ошибки (`LIMIT_EXCEEDED`, `DEBIT_DECLINED`, `TRANSFER_REJECTED`) сразу ведут в компенсацию. Результаты внешних проверок кэшируются в Redis по `paymentId`, поэтому ретрай не вызывает провайдера повторно.
