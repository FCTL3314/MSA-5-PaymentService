# Задание 6. Fitness-функции платёжной системы

Fitness-функции работают двумя способами:
- **в CI** — блокируют merge, если нарушены архитектурные ограничения;
- **в проде** — периодически проверяют инварианты, шлют алерт и, где можно, запускают автоматическое исправление.

Источники данных:
- БД Payment Service: `payments`, `payment_events`, `ledger_entries`;
- REST API и метрики Camunda (экземпляры, инциденты, user tasks, Zeebe metrics);
- выписка банка.

Первая функция уже реализована SQL-запросом на стенде [Task4.2](../Task4.2): см. [logs/payments-final-state.log](../Task4.2/logs/payments-final-state.log), он вернул 0 нарушений.

## Консистентность данных между микросервисами

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
|---|---|---|---|---|
| `TransitAccountZeroBalance` | Деньги не зависают между системами | Для каждого платежа в финальном статусе сумма проводок по транзитному счёту равна 0. Для незавершённого — не больше суммы платежа | Алерт P1 «Финансам» и SRE. Для платежа запускается процесс автоматического возврата / сверки | SQL по `ledger_entries` каждые 5 минут. Метрика `transit_unbalanced_payments` в Prometheus, алерт при > 0 |
| `PaymentSagaStatusConsistency` | Статус платежа совпадает с состоянием оркестратора | Финальный статус платежа ⇔ экземпляр Saga завершён. Промежуточный статус ⇔ экземпляр активен. Нет платежей без экземпляра и экземпляров без платежа | Алерт P2. Если экземпляр завершён, а платёж «висит» — автоматический запрос статуса операций и перезапуск компенсации | Периодическая сверка: `payments` × Camunda `POST /v2/process-instances/search` по `businessId` |
| `BankLedgerReconciliation` | Проводки сервиса совпадают с банком | Каждой операции из выписки банка соответствует проводка с тем же ключом идемпотентности и суммой, и наоборот | Расхождение — в очередь «Финансов». «Осиротевшее» списание без платежа возвращается клиенту автоматически | Ежедневный батч: реестр банка × `ledger_entries`. Отчёт в BI |
| `SingleMoneyOperationPerPayment` | Нет двойных списаний, переводов и возвратов | Для каждого `paymentId` не больше одной проводки каждого типа (`DEBIT`, `TRANSFER`, `REFUND`) | Алерт P1, блокировка выплаты контрагенту до разбора | Уникальный индекс по ключу идемпотентности плюс SQL-проверка `count(*) > 1` в проде и в E2E-тестах CI |

## Выявление «зависших» процессов

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
|---|---|---|---|---|
| `StuckPaymentStatus` | Платёж не застревает в промежуточном статусе | `DEBIT_PENDING` и `TRANSFER_PENDING` не дольше 2 минут. `FRAUD_CHECK_PENDING` — не дольше cut-off + 1 минута. `MANUAL_REVIEW` — не дольше 21 минуты. `COMPENSATING` — не дольше 10 минут | Алерт SRE с `paymentId` и шагом. Для `*_PENDING` — автоматический запрос статуса операции в банке | SQL по `payments (status, updated_at)` раз в минуту. Gauge по статусам в Prometheus, дашборд Grafana |
| `NoOpenSagaIncidents` | Технические сбои не копятся незамеченными | Нет активных инцидентов в `payment-saga`, то есть шагов с исчерпанными ретраями | Алерт P2 с элементом BPMN и текстом ошибки. После исправления — resolve incident, процесс продолжается | Camunda `POST /v2/incidents/search` раз в минуту. Ссылка на экземпляр в Operate |
| `LongRunningSagaInstances` | Ни один экземпляр не живёт дольше бизнес-лимита | Нет активных экземпляров `payment-saga` старше 30 минут (20 минут ручной проверки плюс запас) | Алерт SRE и «Безопасности», разбор в Operate | Camunda `process-instances/search` с фильтром `state = ACTIVE`, `startDate < now − 30m` |
| `JobBacklog` | Шаги не ждут свободного worker | Время от создания job до активации не больше 2 с (p99). Нет job types без активных workers | Автоматическое масштабирование workers. Если workers по типу нет — алерт P1 | Метрики Zeebe (`zeebe_job_*`) в Prometheus плюс heartbeat workers |

## Целостность Saga-транзакций

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
|---|---|---|---|---|
| `CompensationCompleteness` | Каждая отменённая Saga полностью откатила свои шаги | Для `BLOCKED` и `CANCELLED` с проводкой `DEBIT` есть `REFUND` на ту же сумму и снят резерв лимитов. Для `REJECTED` проводок нет | Алерт P1, автоматический повторный запуск `REFUND_FUNDS` / `RELEASE_LIMITS` (они идемпотентны) | SQL по `payments` + `ledger_entries` плюс проверка ключей резерва в Redis |
| `NoCompensationAfterPivot` | После перевода контрагенту откат невозможен | В `payment_events` нет перехода в `COMPENSATING` после `TransferConfirmed`. Нет пары `TRANSFER` + `REFUND` у одного платежа | Алерт P1, разбор инцидента «Безопасностью» и «Финансами» | SQL по `payment_events` / `ledger_entries`. В CI — тест таблицы переходов |
| `StateMachineConformance` | Платёж меняет статус только по утверждённой таблице | Каждая запись `payment_events` (from, to, event) есть в таблице переходов [Task2](../Task2) | В CI — блок merge. В проде — алерт и заморозка платежа | CI-тест сравнивает `TRANSITIONS` в коде с таблицей Task2. В проде — SQL против справочника переходов |
| `BpmnSagaContract` | BPMN-модель соответствует правилам Saga | У каждого шага до pivot есть compensation handler, у pivot и шагов после него — нет. Каждый job type имеет обработчик. Каждый `errorCode` объявлен и перехватывается. У ожиданий (`userTask`, внешние проверки) есть таймер cut-off | Блок merge | CI-тест: парсинг `payment-saga.bpmn` (XML) и сверка с реестром обработчиков. Плюс тест деплоя в Camunda Testcontainer |
| `ArchitectureBoundaries` | Оркестрация не размывает границы доменов | Workers обращаются к доменам только через их API, без чужих БД. Доменные модули не зависят от Camunda SDK. State Machine не зависит от инфраструктуры. Денежные операции вызываются только с ключом идемпотентности | Блок merge | ArchUnit для Java-сервисов, `import-linter` для Python-сервиса прототипа |

## Таймауты и дедлайны бизнес-процессов

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
|---|---|---|---|---|
| `SagaSuccessSla` | SLA успешной транзакции | p90 времени `PaymentInitiated → PaymentCompleted` меньше 5 с за скользящее окно 15 минут | Алерт SRE. Разбор вклада шагов по метрикам каждого job type | Histogram в Prometheus по `payment_events`. В CI — нагрузочный E2E-тест (Task5, № 27) |
| `FraudCutOffEnforced` | Cut-off антифрода срабатывает вовремя и не становится нормой | Время до решения не больше cut-off + 1 с. Доля решений `fraudDecisionSource = CUT_OFF` меньше 2% | Алерт «Безопасности»: при росте доли провайдер деградирует, растёт риск пропустить мошенничество. Включается резервный провайдер | Метрика по переменной `fraudDecisionSource` (лог worker или экспорт Camunda) |
| `ManualReviewDeadline` | Оператор успевает за 20 минут | Нет открытых user tasks `MANUAL_FRAUD_REVIEW` старше 20 минут. Доля задач, закрытых по cut-off, меньше 5% | Алерт руководителю смены операторов. При устойчивом росте — расширение смены | Camunda `POST /v2/user-tasks/search` (`state = CREATED`, `creationDate`) плюс доля событий `ManualReviewCutOffExpired` |
| `InstantRefundDeadline` | Возврат при блокировке действительно мгновенный | От `FraudCheckDenied` / `OperatorDenied` / `CustomerCancelled` до проводки `REFUND` проходит не больше 60 с | Алерт P1, автоматический повторный запуск `REFUND_FUNDS` | SQL по `payment_events` и `ledger_entries`, gauge в Prometheus |
| `ExternalCallTimeoutsConfigured` | Ни один внешний вызов не ждёт бесконечно | У каждого HTTP-клиента к внешним системам задан таймаут не больше 3 с и retry-политика с backoff. В BPMN у каждой задачи задан `retries` | Блок merge | Статическая проверка в CI: клиенты создаются только через фабрику с таймаутом (ArchUnit / линтер), парсинг `retries` в BPMN |
